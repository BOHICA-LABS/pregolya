> **RetryHint precedence rule (F-P28-01, ADV-P1D-PASS-28):** The "Default RetryHint" column above applies only to codes whose per-code catalog row omits a RetryHint. Where a per-code catalog row specifies a RetryHint, the per-code value is authoritative — it overrides the category default. Intentional divergences must carry a BC-anchored rationale in the per-code row or a correction note. Examples: E-RETRY-003 (CircuitBreakerOpen, POLICY) carries `Later(<reset_timeout>)` because the circuit-breaker cool-down semantics of BC-2.16.003 override the POLICY `Never` default — the breaker trip is a temporary state with a known reset horizon; E-CRON-003 (ScheduleQueueFull, POLICY) carries `Later` because schedule queue overflow is a transient capacity condition — the next firing cycle will likely have capacity, making `Later` the correct semantics and a justified override of the POLICY `Never` default per BC-2.12.004 (F-P29-02, ADV-P1D-PASS-29); E-MEMORY-002/005 and E-BUDGET-002 (DURABILITY codes) carry `Never` because their specific failure modes (storage-full, partial-erasure, journal-write) are non-recoverable by retry without operator intervention. Divergences are intentional; the per-code value is the implementation contract. E-MCP-005 (McpServerBindFailed, TRANSPORT) carries `Never` because a socket bind failure (EADDRINUSE, EACCES) requires operator configuration change — the same bind address/port will fail immediately on retry; `Later` (TRANSPORT default) would be misleading per BC-2.09.006 (D20 sub-burst 2); E-TOOLS-004 (BashTimeout, TIMEOUT) carries `Never` because retrying with the same command and same max_duration will produce the same timeout result — recovery requires either increasing max_duration or fixing the command; `Later` (TIMEOUT default) would be misleading per BC-2.23.005 (D23/2026-07-22); E-SERVER-019 (RunQueueFull, POLICY) carries `Later` because run queue overflow is a transient capacity condition — a queue slot opens when the current in_progress run transitions to a terminal state, making `Later` the correct semantics and a justified override of the POLICY `Never` default per BC-2.12.003 PC-004 (ADR-028 Decision 3, burst-A-error-coord/2026-08-26); this mirrors the E-CRON-003 ScheduleQueueFull pattern (same transient-capacity rationale, same POLICY-→-Later override).

> **Authorization-failure categorization rule (OBS-P105-A, 2026-07-18):** Three authorization-failure codes span two categories: E-GRAPH-013 InsufficientApproverRole is **SECURITY**; E-MEMORY-003 ScopeAccessDenied and E-MEMORY-006 InsufficientPrivilege are **POLICY**. The split is intentional — the deciding criterion is whether insufficient authorization could enable a *security attack vector* vs. whether it enforces a *capability or data-access policy constraint*. **SECURITY** applies when the authorization check guards a boundary whose bypass could allow a concrete security violation: E-GRAPH-013 guards HITL risk-tier approval — a caller lacking the required approver role could authorize a high-risk external action if not blocked (BC-2.05.006 risk-tier enforcement gate). **POLICY** applies when the check enforces a data-access or operational capability rule for an otherwise-legitimate caller: E-MEMORY-003 enforces the cross-scope memory isolation policy — caller identity cannot write to another owner's scope (BC-2.15.002); E-MEMORY-006 enforces the admin-only GDPR erasure capability constraint (BC-2.15.003). Decision heuristic: if bypassing the check would allow an *attack vector* (harmful action approval, data poisoning, workspace escape) → **SECURITY**; if it rejects a *privileged operation* for a caller who lacks the required capability or scope right → **POLICY**.

| degraded | Partial result possible; caller may choose to surface partial data | Err with partial payload |
| cosmetic | Display or formatting issue only | Warning log; operation succeeds |

BC-2.23.003 {EC-007} (fuzzy_threshold out of range) and BC-2.23.005 {EC-008} (max_duration=0) / {EC-009} (max_output_bytes=0) are the authoritative raise sites. |

## RFC-7807 Problem Emission

All `PregolyaError` values must be emittable as RFC-7807 problem+json when surfaced
via HTTP (pregolya-server). The mapping is:

| PregolyaError field | RFC-7807 field |
|-----------------------|---------------|
| code (e.g., E-GRAPH-001) | `type` (URI: `urn:pregolya:error:<code>`) |
| message | `detail` |
| category | `title` (humanized category name) |
| component | embedded in `type` URI |
| retry_hint | `extensions.retry_hint` (never/maybe/later) |

## RetryHint Values

| Value | Meaning | Client Behavior |
|-------|---------|----------------|
| `Never` | Retrying will not help; caller must fix input or config | Do not retry |
| `Maybe` | Retry once with same input; transient errors only | Retry once, then give up |
| `Later(Duration)` | Rate limit or temporary unavailability; wait and retry | Respect backoff |
