# VP-001: BSP Super-Step Determinism

## Property Statement

For any fixed set of super-step task outputs, the reduced channel state is identical
regardless of the order in which tasks complete.

**Formal invariant (DI-001):** `reduce(sort_by_task_id(tasks)) == reduce(sort_by_task_id(permute(tasks)))`

Because `sort_by_task_id` produces the same order regardless of input order, the reducer
application is deterministic.

## Source Contract

- **BC:** BC-2.03.001 — BSP Super-Step Execution Determinism — Kani VP Seed (NE-17)
- **Postcondition/Invariant:** Invariant DI-001 — Identical inputs always produce identical `GraphState` regardless of node completion order. Reducer application order is determined by a deterministic sort of `(task_id, channel_name)` — lexicographic ascending — not by task completion arrival order. Concurrent writes to a `LastValue` channel from the same super-step raise `InvalidUpdateError`, not a silent race.

## Proof Harness Skeleton

Target file: `ferrochain-graph/src/bsp_engine.rs` (or adjacent `proof` module)

```rust
// ferrochain-graph/src/proofs/bsp_determinism.rs

#[cfg(kani)]
mod proofs {
    use super::*;

    /// VP-001: BSP Super-Step Determinism
    /// Proves: for any permutation of task outputs, sorted reduce produces identical channel state.
    #[kani::proof]
    fn bsp_determinism_harness() {
        // Bound: n ≤ 4 tasks to keep state-space tractable for model checking
        let n: usize = kani::any();
        kani::assume(n > 0);
        kani::assume(n <= 4);

        // Symbolic task IDs and their channel updates
        let task_ids: Vec<TaskId> = (0..n).map(|i| TaskId(i as u64)).collect();
        let updates: Vec<ChannelUpdate> = (0..n)
            .map(|_| kani::any::<ChannelUpdate>())
            .collect();

        let task_outputs: Vec<(TaskId, ChannelUpdate)> =
            task_ids.into_iter().zip(updates).collect();

        // Arbitrary permutation of task outputs
        let permutation: Vec<usize> = kani::any_permutation(n);
        let permuted: Vec<(TaskId, ChannelUpdate)> =
            permutation.iter().map(|&i| task_outputs[i].clone()).collect();

        // Both orderings must produce the same reduced state
        let result_a = reduce_super_step(task_outputs.clone());
        let result_b = reduce_super_step(permuted);

        kani::assert(result_a == result_b, "BSP determinism violated");
    }

    /// Negative invariant: concurrent LastValue writes from same super-step → InvalidUpdateError
    #[kani::proof]
    fn concurrent_last_value_write_rejection() {
        let channel: ChannelName = kani::any();
        let update1: LastValueUpdate = kani::any();
        let update2: LastValueUpdate = kani::any();

        // Two writes to the same LastValue channel in the same super-step
        let result = apply_last_value_updates(&channel, &[update1, update2]);

        // Must be Err(InvalidUpdateError), never silent clobber
        kani::assert(
            matches!(result, Err(FerrochainError { code: "E-GRAPH-001", .. })),
            "Concurrent LastValue write must return InvalidUpdateError"
        );
    }
}
```

## Feasibility Assessment

**Feasibility: HIGH**

Key factors:
1. `reduce_super_step` is a pure function: takes `Vec<(TaskId, ChannelUpdate)>`, returns `ChannelState`. No async, no I/O.
2. Task-identity sort (`sort_by_key(|t| t.0)`) produces a total order; Kani can verify this terminates.
3. Bounded by n ≤ 4: a 4-task super-step generates 4! = 24 permutations. State space is tractable.
4. `ChannelUpdate` must implement `kani::Arbitrary`; this requires bounded symbolic values.

| Factor | Assessment | Notes |
|--------|-----------|-------|
| Input space size | Bounded | n ≤ 4 tasks; `ChannelUpdate` fields constrained with bounded symbolic values |
| Proof complexity | Low-medium | Permutation check over sort-then-reduce; no unbounded loops |
| Tool support | Supported | Kani 0.67.0; `reduce_super_step` is a pure function; `kani::Arbitrary` derivable |
| Estimated proof time | < 5 min | 24 permutations × bounded field space; within CI budget |

**Known constraint:** `kani::any_permutation` is not a built-in Kani API; the harness will need
to use a known-size permutation array (`let perm: [usize; 4]`) with bounds checking. Implementation
will need to adapt the skeleton.

**Blocking risk:** If `ChannelUpdate` contains unbounded heap data (e.g., `String`), Kani
will require bounded string lengths. The implementer must use `kani::vec(n, || kani::any::<u8>())`
patterns for symbolic strings.

- [ ] `ChannelUpdate` implements `kani::Arbitrary` with bounded inner data
