# VP-001: BSP Super-Step Determinism

## Property Statement

For any fixed set of super-step task outputs, the reduced channel state is identical
regardless of the order in which tasks complete.

**Formal invariant (DI-001):** `reduce(sort_by_key((task_id, channel_name))(tasks)) == reduce(sort_by_key((task_id, channel_name))(permute(tasks)))`

Because `sort_by_key(|(task_id, channel_name)| (task_id.as_str(), channel_name.as_str()))`
— lexicographic ascending over both fields — produces the same total order regardless of
input order, the reducer application is deterministic. `task_id` is the primary sort key
and `channel_name` is the tiebreaker, per BC-2.03.001 §Invariants and BC-2.03.003 §PC-1.
The lexicographic model is required: a numeric `TaskId(u64)` cannot exhibit the ordering
hazard `"10" < "9"` (lexicographic) vs `10 > 9` (numeric), which is the class of defect
this proof is designed to exclude (BC-2.03.003 §Reference: "sort is on the string
representation of the task ID — matching Python's default string comparison").

## Source Contract

- **BC:** BC-2.03.001 — BSP Super-Step Execution Determinism — Kani VP Seed (NE-17)
- **Postcondition/Invariant:** Invariant DI-001 — Identical inputs always produce identical `GraphState` regardless of node completion order. Reducer application order is determined by a deterministic sort of `(task_id, channel_name)` — lexicographic ascending — not by task completion arrival order. Concurrent writes to a `LastValue` channel from the same super-step raise `InvalidUpdateError`, not a silent race.

## Proof Harness Skeleton

Target file: `ferrochain-graph/src/bsp_engine.rs` (or adjacent `proof` module)

```rust
// ferrochain-graph/src/proofs/bsp_determinism.rs

#[cfg(kani)]
mod proofs {
    use super::*;

    /// VP-001: BSP Super-Step Determinism
    /// Proves: for any permutation of task outputs, lexicographic sort by (task_id, channel_name)
    /// produces identical channel state regardless of task arrival order.
    ///
    /// Sort key: (task_id: &str, channel_name: &str) — lexicographic ascending.
    /// BC-2.03.001 §Invariants: "No floating-point, random, or wall-clock component may enter the sort key."
    /// BC-2.03.003 §Reference: "sort is on the string representation — Python's default string comparison."
    /// TaskId is modeled as String (not u64) to expose lexicographic hazards:
    /// "10" < "9" (lex) but 10 > 9 (numeric) — a numeric model cannot find this defect class.
    #[kani::proof]
    fn bsp_determinism_harness() {
        // Bound: n ≤ 4 tasks to keep state-space tractable for model checking
        let n: usize = kani::any();
        kani::assume(n > 0);
        kani::assume(n <= 4);

        // Symbolic task IDs as bounded ASCII strings — models lexicographic ordering hazards.
        // Sort key: (task_id: &str, channel_name: &str) — lexicographic ascending.
        let task_outputs: Vec<(TaskId, String, ChannelUpdate)> = (0..n).map(|_| {
            // task_id: bounded alphanumeric string (length 1..=4)
            let id_len: usize = kani::any();
            kani::assume(id_len >= 1 && id_len <= 4);
            let task_id_str: String = (0..id_len).map(|_| {
                let c: u8 = kani::any();
                kani::assume(c.is_ascii_alphanumeric());
                c as char
            }).collect();
            // channel_name: bounded alphanumeric string (length 1..=4) — tiebreaker key
            let ch_len: usize = kani::any();
            kani::assume(ch_len >= 1 && ch_len <= 4);
            let channel_name: String = (0..ch_len).map(|_| {
                let c: u8 = kani::any();
                kani::assume(c.is_ascii_alphanumeric());
                c as char
            }).collect();
            (TaskId(task_id_str), channel_name, kani::any::<ChannelUpdate>())
        }).collect();

        // Bounded permutation: [usize; 4] array with modulo n index
        // (kani::any_permutation(n) is not a built-in Kani API — see §Feasibility)
        let perm: [usize; 4] = kani::any();
        let permuted: Vec<(TaskId, String, ChannelUpdate)> =
            (0..n).map(|i| task_outputs[perm[i] % n].clone()).collect();

        // Both orderings must produce the same reduced state after sort-then-reduce.
        // reduce_super_step internally sorts by (task_id.as_str(), channel_name.as_str()) lex asc.
        let result_a = reduce_super_step(task_outputs.clone());
        let result_b = reduce_super_step(permuted);

        kani::assert(result_a == result_b, "BSP determinism violated");
    }

    /// Negative invariant: concurrent LastValue writes from same super-step → InvalidUpdateError
    #[kani::proof]
    fn concurrent_last_value_write_rejection() {
        let channel: ChannelName = kani::any();
        let update1: LastValueUpdate = kani::any();
        let update2: LastValueUpdate = kani::any();

        // Two writes to the same LastValue channel in the same super-step
        let result = apply_last_value_updates(&channel, &[update1, update2]);

        // Must be Err(InvalidUpdateError), never silent clobber
        kani::assert(
            matches!(result, Err(FerrochainError { code: "E-GRAPH-001", .. })),
            "Concurrent LastValue write must return InvalidUpdateError"
        );
    }
}
```

## Feasibility Assessment

**Feasibility: HIGH**

Key factors:
1. `reduce_super_step` is a pure function: takes `Vec<(TaskId, ChannelUpdate)>`, returns `ChannelState`. No async, no I/O.
2. Sort key `(task_id: &str, channel_name: &str)` lexicographic ascending produces a total order; Kani can verify this terminates. String-based `TaskId` is required by BC-2.03.003 §Reference (lexicographic UTF-8 order); numeric `TaskId(u64)` cannot model the lexicographic ordering hazard.
3. Bounded by n ≤ 4: a 4-task super-step generates 4! = 24 permutations. State space is tractable.
4. `ChannelUpdate` must implement `kani::Arbitrary`; this requires bounded symbolic values.

| Factor | Assessment | Notes |
|--------|-----------|-------|
| Input space size | Bounded | n ≤ 4 tasks; `ChannelUpdate` fields constrained with bounded symbolic values |
| Proof complexity | Low-medium | Permutation check over sort-then-reduce; no unbounded loops |
| Tool support | Supported | Kani 0.67.0; `reduce_super_step` is a pure function; `kani::Arbitrary` derivable |
| Estimated proof time | < 5 min | 24 permutations × bounded field space; within CI budget |

**Known constraint:** `kani::any_permutation` is not a built-in Kani API; the harness will need
to use a known-size permutation array (`let perm: [usize; 4]`) with bounds checking. Implementation
will need to adapt the skeleton.

**Blocking risk:** If `ChannelUpdate` contains unbounded heap data (e.g., `String`), Kani
will require bounded string lengths. The implementer must use `kani::vec(n, || kani::any::<u8>())`
patterns for symbolic strings.

## Proof Obligations

- [ ] `ChannelUpdate` implements `kani::Arbitrary` with bounded inner data
