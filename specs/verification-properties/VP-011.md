# VP-011: PreToolCallHook Fail-Closed — Deny Excludes tool.invoke; Hook Panic/Error Treated as Deny

## Property Statement

For any `PreToolDecision::Deny { reason }` outcome — whether returned by the hook's
`pre_invoke` call or synthesized by the panic-shield when `pre_invoke` panics or returns
an error — `pre_tool_dispatch` returns `ToolOutput::Error(reason)` and never calls
`tool.invoke`. The `tool.invoke` call site is structurally unreachable from the Deny
branch of `route_pre_tool_decision`.

**Formal invariant (DI-014):**
```
∀ decision: PreToolDecision:
  decision == Deny { reason } →
    route_pre_tool_decision(decision) == DispatchOutcome::Reject(reason)
    ∧ route_pre_tool_decision(decision) ≠ DispatchOutcome::Proceed(_)

∀ hook_result: Result<PreToolDecision, HookError>:
  hook_result == Err(_) →
    shield_hook_result(hook_result) == PreToolDecision::Deny { .. }
    ∧ route_pre_tool_decision(shield_hook_result(hook_result)) == DispatchOutcome::Reject(_)
```

`tool.invoke` is called only when `route_pre_tool_decision` returns
`DispatchOutcome::Proceed(_)`. The Deny branch reaches `DispatchOutcome::Reject(_)` and
`DispatchOutcome::Proceed(_)` is structurally unreachable from that arm. This is a pure
control-flow reachability property provable by exhaustive symbolic execution.

No code path through `pre_tool_dispatch` produces a tool invocation after a Deny decision
or a hook panic. `AlwaysApprovePolicy` (the default hook when none is configured) always
returns `Approve` and is not affected by this invariant.

**Design note — PendingHumanApproval (Option A peel-off):** `PreToolDecision::PendingHumanApproval { prompt }` is
peeled off by the async `pre_tool_dispatch` wrapper BEFORE `route_pre_tool_decision` is
called. When the hook returns `PendingHumanApproval`, the wrapper issues
`interrupt(ToolApprovalRequest{..})` and suspends the run via BC-2.05.001 machinery without
calling `route_pre_tool_decision`. If `PendingHumanApproval` unexpectedly reaches
`route_pre_tool_decision` (should not occur by design), the `#[non_exhaustive]` wildcard arm
returns `DispatchOutcome::Reject(_)` (fail-closed). The `PendingHumanApproval`
non-invocation guarantee is a behavioral property covered by BC-2.05.008 integration tests,
not the Kani harness.

## Source Contract

- **BC:** BC-2.05.007 — PreToolCallHook Dispatch — pre_invoke Contract; Approve/Deny/Edit/PendingHumanApproval; Fail-Closed Deny (VP-011 Kani Seed)
- **Postcondition 2 (Deny):** `pre_tool_dispatch` constructs `ToolOutput::Error(reason)` and returns it WITHOUT calling `tool.invoke(A)`. The tool is not invoked.
- **Postcondition 5 (Hook error):** If `hook.pre_invoke(...)` panics or returns an error, `pre_tool_dispatch` treats this as `Deny { reason: "hook error: <detail>" }`.
- **Invariant — Fail-closed Deny:** `PreToolDecision::Deny` ALWAYS results in `ToolOutput::Error(reason)` being returned WITHOUT invoking the tool. Under no control flow path does a Deny decision allow tool execution.
- **Invariant — DI-014:** `ToolOutput::Error(reason)` is returned to the model context on Deny; the Deny reason is never silently discarded.
- **TV-002:** Hook returns `Deny { reason: "not allowed" }` → `ToolOutput::Error("not allowed")` — tool NOT invoked.
- **TV-006:** Hook panics → `ToolOutput::Error("hook error: ...")` — tool not invoked.
- **Postcondition 7 (Pure Routing Core):** The implementation MUST extract
  `route_pre_tool_decision(decision: PreToolDecision) -> DispatchOutcome` and
  `shield_hook_result(result: Result<PreToolDecision, HookError>) -> PreToolDecision` as named
  pure-core synchronous functions in `graph::hitl`; `DispatchOutcome` (with
  `Proceed(Option<serde_json::Value>)` and `Reject(String)` variants) defined therein. These are
  the formal Kani proof targets. The async `pre_tool_dispatch` wrapper is NOT a Kani proof target
  (Kani 0.67.0 has no native async support). PC-7 is the source-of-truth for the proof surface
  named in this VP's §Proof Obligations and §Proof Harness Skeleton.

## Proof Method

| Method | Tool | Bounded? | Coverage |
|--------|------|----------|----------|
| Model checking | Kani 0.67.0 | Yes — `PreToolDecision` is a 4-variant `#[non_exhaustive]` enum; the three routable variants (Deny, Approve, Edit) plus hook-error path are covered by four concrete proof functions; `PendingHumanApproval` is peeled off upstream in `pre_tool_dispatch` — the `#[non_exhaustive]` wildcard arm handles any un-peeled variant with fail-closed Reject | The three routable `PreToolDecision` variants (Deny/Approve/Edit) and hook-error path; proves `DispatchOutcome::Proceed(_)` is unreachable from `Deny { .. }` and `HookError`; `PendingHumanApproval` path handled by async wrapper (BC-2.05.008 integration tests, not Kani scope) |

**Kani async constraint (Kani 0.67.0 has NO native async support):** `pre_tool_dispatch` is
`async` (it must `await` the hook's `pre_invoke` call per ADR-018 Decision 3). The Kani
harness does NOT target `pre_tool_dispatch` directly. Instead, the proof targets two
extracted **pure-core synchronous functions** that encapsulate the routing logic:

1. `route_pre_tool_decision(decision: PreToolDecision) -> DispatchOutcome` — the pure
   dispatch branch (steps 3–5 of the 6-step dispatch sequence in ADR-018 Decision 3,
   §"Dispatch in graph::hitl::pre_tool_dispatch"). This function is sync; no I/O; no
   awaiting.

2. `shield_hook_result(result: Result<PreToolDecision, HookError>) -> PreToolDecision` — the
   panic-shield conversion (step 2 of the dispatch sequence). When `result` is `Err(_)`,
   returns `PreToolDecision::Deny { reason: "hook error: ..." }`. When `result` is `Ok(d)`,
   returns `d`. This function is pure-core sync.

The implementer must extract these as named, standalone, synchronous functions so the Kani
harness can call them directly. The async `pre_tool_dispatch` wrapper calls them in sequence;
the sequential composition is behaviorally equivalent and does not require Kani to handle
`async fn`.

**Harness boundary:** The proof covers `route_pre_tool_decision` and `shield_hook_result` as
extracted pure functions. The async `pre_tool_dispatch` wrapper (which awaits `pre_invoke`)
is excluded from the Kani scope. The proof establishes that the routing invariant holds for
all possible decision outcomes; the async wrapper's correctness is covered by behavioral
integration tests (TV-001 through TV-006 in BC-2.05.007).

**`#[non_exhaustive]` handling:** `PreToolDecision` is `#[non_exhaustive]`. The harness uses
concrete variant construction for the three routable variants (Deny, Approve, Edit) and a
separate proof for hook-error paths rather than `kani::any::<PreToolDecision>()`.
`PendingHumanApproval` is peeled off upstream in `pre_tool_dispatch` before
`route_pre_tool_decision` is called (Option A dispatch design); this variant does NOT have a
dedicated Kani proof function. The `#[non_exhaustive]` wildcard arm in
`route_pre_tool_decision` returns `DispatchOutcome::Reject(_)` for any variant that reaches
it unexpectedly — including `PendingHumanApproval` and any future variants (fail-closed
forward safety). When new variants are added to `PreToolDecision`, their dispatch layer
(async wrapper vs. routing function) must be specified before adding a harness.

## Proof Harness Skeleton

Harness file: `pregolya-graph/src/proofs/pre_tool_hook.rs` — Kani harness (`deny_excludes_tool_invocation`).
Proof-target module: `pregolya-graph/src/hitl.rs` — pure functions under formal proof (`route_pre_tool_decision`, `shield_hook_result`, `DispatchOutcome`).

```rust
// pregolya-graph/src/proofs/pre_tool_hook.rs
// Target functions: graph::hitl::route_pre_tool_decision, graph::hitl::shield_hook_result
//
// Dispatch design (Option A peel-off): `PendingHumanApproval` is handled by the async
// `pre_tool_dispatch` wrapper BEFORE `route_pre_tool_decision` is called. The wrapper issues
// `interrupt(ToolApprovalRequest{..})` and suspends the run; `route_pre_tool_decision` is
// not invoked for `PendingHumanApproval` in normal operation. If `PendingHumanApproval` ever
// reaches `route_pre_tool_decision` (unexpected), the `#[non_exhaustive]` wildcard arm returns
// `DispatchOutcome::Reject(_)` (fail-closed). No dedicated proof function for `PendingHumanApproval`.

#[cfg(kani)]
mod proofs {
    use super::*;

    /// VP-011 (Part 1): Deny decision ALWAYS produces Reject — tool.invoke unreachable.
    /// Proves: route_pre_tool_decision(Deny { .. }) == DispatchOutcome::Reject(_)
    ///         and DispatchOutcome::Proceed(_) is unreachable from the Deny arm.
    #[kani::proof]
    fn deny_excludes_tool_invocation() {
        // reason content does not affect routing — branch is variant-based.
        // Use a concrete string (Kani String symbolic is expensive; branch proof is independent of content).
        let reason = "denied by hook".to_string();
        let decision = PreToolDecision::Deny { reason: reason.clone() };

        let outcome = route_pre_tool_decision(decision);

        // Primary invariant: Deny → Reject
        kani::assert(
            matches!(outcome, DispatchOutcome::Reject(_)),
            "Deny decision MUST produce DispatchOutcome::Reject"
        );
        // Secondary invariant: Proceed is structurally unreachable from Deny
        kani::assert(
            !matches!(outcome, DispatchOutcome::Proceed(_)),
            "tool.invoke (Proceed) MUST be unreachable for Deny decision"
        );
    }

    /// VP-011 (Part 2): Approve decision routes to Proceed (positive sanity check).
    /// Ensures route_pre_tool_decision is not trivially reject-everything.
    #[kani::proof]
    fn approve_reaches_tool_invocation() {
        let decision = PreToolDecision::Approve;
        let outcome = route_pre_tool_decision(decision);
        kani::assert(
            matches!(outcome, DispatchOutcome::Proceed(_)),
            "Approve decision MUST reach tool.invoke (DispatchOutcome::Proceed)"
        );
    }

    /// VP-011 (Part 3): Hook panic/error → Deny → Reject (fail-closed chain).
    /// Proves: shield_hook_result(Err(_)) → Deny → Reject.
    #[kani::proof]
    fn hook_error_resolves_to_deny_and_reject() {
        let error_detail = "panic in hook".to_string();
        let hook_result: Result<PreToolDecision, HookError> =
            Err(HookError::Panic(error_detail));

        // Step 1: panic-shield converts Err → Deny
        let effective_decision = shield_hook_result(hook_result);
        kani::assert(
            matches!(effective_decision, PreToolDecision::Deny { .. }),
            "hook panic MUST be converted to PreToolDecision::Deny"
        );

        // Step 2: Deny routes to Reject
        let outcome = route_pre_tool_decision(effective_decision);
        kani::assert(
            matches!(outcome, DispatchOutcome::Reject(_)),
            "hook panic → Deny → Reject (tool.invoke unreachable)"
        );
        kani::assert(
            !matches!(outcome, DispatchOutcome::Proceed(_)),
            "tool.invoke (Proceed) MUST be unreachable after hook panic"
        );
    }

    /// VP-011 (Part 4): Edit with invalid args falls back to Deny → Reject.
    /// Proves: Edit { modified_args: not-a-JSON-object } → DispatchOutcome::Reject(_).
    #[kani::proof]
    fn edit_invalid_args_falls_back_to_deny() {
        // A JSON string (not a JSON object) is invalid for Edit modified_args
        let invalid_args = serde_json::Value::String("not-an-object".to_string());
        let decision = PreToolDecision::Edit { modified_args: invalid_args };

        let outcome = route_pre_tool_decision(decision);
        kani::assert(
            matches!(outcome, DispatchOutcome::Reject(_)),
            "Edit with non-object modified_args MUST fall back to Reject"
        );
        kani::assert(
            !matches!(outcome, DispatchOutcome::Proceed(_)),
            "tool.invoke MUST be unreachable for invalid Edit args"
        );
    }
}
```

## Feasibility Assessment

**Feasibility: HIGH**

| Factor | Assessment | Notes |
|--------|-----------|-------|
| Input space size | Bounded | `PreToolDecision` is a 4-variant enum (+ future non_exhaustive variants); routing is a pattern-match over the variant — trivially bounded |
| Proof complexity | Low | The routing is a single `match` expression; each arm is a constant constructor call; no arithmetic, no loops, no I/O |
| Tool support | Supported | Kani 0.67.0; both `route_pre_tool_decision` and `shield_hook_result` are pure-core sync; `serde_json::Value` pattern matching is tractable |
| Estimated proof time | < 2 min | Pattern-match proof over a small enum; CBMC solves trivial branch reachability queries in seconds |

Key factors:
1. Both proof-target functions are pure-core synchronous. No async, no I/O, no state. Kani 0.67.0
   compatible without adaptation.
2. The routing proof is structurally simple: a `match` with four arms. CBMC's SAT solver handles
   this as a trivial conditional reachability query — is there a code path from the `Deny { .. }`
   arm to the `DispatchOutcome::Proceed(_)` constructor? The answer is no by construction.
3. The panic-shield proof is equally simple: `Err(_)` always maps to `Deny { .. }`, which
   then maps to `Reject(_)`. Two function calls, no loops.
4. `serde_json::Value` for Part 4 (invalid Edit args) may require a Kani stub if `serde_json`
   is not natively modeled. The implementer may use a lightweight `is_json_object(v: &Value) -> bool`
   extraction that avoids the full serde_json model.

**Known constraint:** `#[non_exhaustive]` on `PreToolDecision` means future variants not
handled by the `pre_tool_dispatch` async wrapper will require harness extension to prove their
routing invariant. The current proof covers three D23-defined routable variants (`Approve`,
`Deny`, `Edit`) via concrete proof functions plus the hook-error chain. `PendingHumanApproval`
is not a harness target — it is peeled off upstream in the async `pre_tool_dispatch` wrapper
before `route_pre_tool_decision` is called; the `#[non_exhaustive]` wildcard arm provides
fail-closed Reject safety for `PendingHumanApproval` if it reaches `route_pre_tool_decision`
unexpectedly.

**Blocking risk (LOW):** `serde_json::Value` in Part 4 may be opaque to CBMC if serde_json internals
are not modeled. The recommended mitigation is extracting `validate_edit_args(v: &serde_json::Value) -> bool`
as a standalone function and testing it with a symbolic boolean rather than symbolic `serde_json::Value`.
This keeps the proof tractable while covering the invariant.
