# VP-010: Reviver Allowlist Containment — Non-Monolith Unregistered Type Id Returns Err(E-SRLZ-001); Ok is Unreachable

## Property Statement

**Kani-proven scope (this VP):** For all type-id paths not present in the registered allowlist
AND not present in `LANGCHAIN_MONOLITH_TYPES`, `allowlist_check` returns `Err(E-SRLZ-001)` and
no `Ok(())` is produced. The proof is over `allowlist_check` (an extracted pure function), not
over `revive()` directly.

**Broader invariant (jointly proven):** For ALL unregistered ids — including monolith types —
`revive()` returns `Err`, never `Ok`. This joint coverage is provided by:
- VP-010 (this VP): non-monolith unregistered ids → `Err(E-SRLZ-001)` via `allowlist_check`
- BC-2.19.006 unit tests: monolith ids → `Err(E-SRLZ-002)` via `LANGCHAIN_MONOLITH_TYPES` check in `revive()`

**Why the scope is restricted:** BC-2.19.006 PC4(c) defines a LANGCHAIN_MONOLITH_TYPES check
that runs after `allowlist_check` in `revive()` and returns `Err(E-SRLZ-002)` for known-monolith
ids. Those ids are also "not in registry" but return E-SRLZ-002, not E-SRLZ-001. Including them
in the Kani harness would require modeling `LANGCHAIN_MONOLITH_TYPES` and asserting E-SRLZ-002 as
an alternative outcome — which is correct behavior but outside the `allowlist_check` boundary.
Restricting the symbolic domain to non-monolith ids keeps the proof clean and the assertion single-valued.

**Formal invariant (DI-014) — restricted domain:**
```
∀ id: &[String],
  registry: &HashMap<Vec<String>, ()> (5 concrete entries),
  monolith_set: &HashSet<Vec<String>> (modeled as empty — id ∉ monolith_set by assume):
    !registry.contains_key(id) ∧ !monolith_set.contains(id)
    → allowlist_check(id, registry) == Err(FerrochainError { code: "E-SRLZ-001" })
    ∧ allowlist_check(id, registry) ≠ Ok(_)
```

The allowlist check is the first operation in `revive()` — no constructor is called, no
`kwargs` map is parsed, and no heap allocation beyond the error struct itself occurs on the
failure path. This is the primary deserialization security invariant (ADR-016 Decision 3
Property 1).

## Source Contract

- **BC:** BC-2.19.005 — Reviver Allowlist Containment — Unregistered Type Id Raises E-SRLZ-001 (Fail-Closed, VP-010 Kani Candidate)
- **Postcondition 1:** `Err(FerrochainError { code: "E-SRLZ-001", category: SECURITY })` when id is not in registry.
- **Postcondition 2:** No constructor called; no kwargs parsed; no heap allocation on failure path beyond error struct.
- **Postcondition 3:** Error propagates via `?`; not swallowed or converted within `core::serializable`.
- **Invariant 1:** The allowlist check is the **first operation** in `revive()` — unreorderable.
- **Invariant 2:** The check uses the same `HashMap` populated at startup — no `allow_all` flag, no runtime override.
- **Invariant 3:** `category: Category::SECURITY` — this is a security error, not a validation error.
- **TV-001/002 (Red Gate):** Attacker-crafted ids (`["attacker_custom", "Exploit"]`) and empty ids (`[]`) both return `Err(E-SRLZ-001)`.

## Proof Method

| Method | Tool | Bounded? | Coverage |
|--------|------|----------|----------|
| Model checking | Kani 0.67.0 | Yes — registry modeled as a fixed bounded HashMap with N ≤ 5 registered entries; symbolic `id: Vec<String>` with length ≤ 4 and each string length ≤ 16 bytes | All symbolic `Serialized` inputs where the id is not in the bounded registry; proves that the `Ok` arm of `revive()` is unreachable when id is absent from the registry |

**Kani async constraint (Kani 0.67.0 has NO native async support):** `Reviver::revive()` is
a pure-core synchronous function — no I/O, no async (BC-2.19.005: "pure-core (no I/O, no async)";
ADR-016 Decision 3 Property 1). The harness calls `revive()` directly without any `.await`
or Tokio runtime. No `block_on` adaptation needed.

**Registry modeling for Kani:** The `OnceLock<HashMap<Vec<String>, &LcEntry>>` cannot be
symbolically explored by Kani as-is (linker-section initialization is opaque to the model
checker). The harness instead calls an extracted pure function
`allowlist_check(id: &[String], registry: &HashMap<Vec<String>, ()>) → Result<(), FerrochainError>`
that is the heart of the security property. The harness constructs a symbolic registry with
N ≤ 5 known entries (e.g., `["langchain_core", "prompts", "PromptTemplate"]`) and proves
that any id NOT among them returns `Err(E-SRLZ-001)`.

**Harness boundary:** The proof covers `allowlist_check` as the extracted pure-core gate.
The full `revive()` function (which calls `allowlist_check` as its first step, then dispatches
to constructors) is excluded from the Kani scope beyond the allowlist gate itself. The
implementer must extract `allowlist_check` as a named, standalone function so the harness
can import and call it directly. This is the same pure-core extraction pattern used for VP-006.

**LANGCHAIN_MONOLITH_TYPES exclusion:** The symbolic domain for this harness explicitly
excludes monolith-type ids by adding `kani::assume(!monolith_set.contains(&id))` or by
constructing ids that provably fall outside the monolith set. Monolith ids are unregistered
AND produce `Err(E-SRLZ-002)` via a separate check in `revive()` (BC-2.19.006). Including
them in this harness would require asserting E-SRLZ-002 as an additional outcome, which is
correct behavior but outside the `allowlist_check` boundary being proven here. The joint
"never Ok for any unregistered id" invariant is established by VP-010 + BC-2.19.006 tests together.

## Proof Harness Skeleton

Target file: `ferrochain-core/src/serializable.rs`

```rust
// ferrochain-core/src/proofs/reviver_allowlist.rs

#[cfg(kani)]
mod proofs {
    use super::*;
    use std::collections::HashMap;

    /// VP-010: Reviver Allowlist Containment
    /// Proves: unregistered id ALWAYS returns Err(E-SRLZ-001); Ok is unreachable.
    #[kani::proof]
    fn allowlist_rejects_unregistered_id() {
        // Model a fixed registry with N ≤ 5 known entries
        // Concrete registered ids (representative sample from the 141-type corpus)
        let mut registry: HashMap<Vec<String>, ()> = HashMap::new();
        registry.insert(vec!["langchain_core".to_string(), "prompts".to_string(), "PromptTemplate".to_string()], ());
        registry.insert(vec!["langchain_core".to_string(), "messages".to_string(), "SystemMessage".to_string()], ());
        registry.insert(vec!["langchain_core".to_string(), "messages".to_string(), "HumanMessage".to_string()], ());
        registry.insert(vec!["langchain_core".to_string(), "messages".to_string(), "AIMessage".to_string()], ());
        registry.insert(vec!["langchain_core".to_string(), "chat_history".to_string(), "InMemoryChatMessageHistory".to_string()], ());

        // Symbolic id: bounded length to keep state space finite
        let n_segments: usize = kani::any();
        kani::assume(n_segments <= 4); // id path depth ≤ 4 segments

        // Each segment is a bounded symbolic string (length ≤ 16 bytes, ASCII printable)
        let id: Vec<String> = (0..n_segments).map(|_| {
            let len: usize = kani::any();
            kani::assume(len <= 16);
            // Symbolic string over bounded ASCII (simplified for Kani tractability)
            let bytes: Vec<u8> = (0..len).map(|_| {
                let b: u8 = kani::any();
                kani::assume(b >= 0x20 && b <= 0x7e); // printable ASCII
                b
            }).collect();
            String::from_utf8(bytes).unwrap_or_default()
        }).collect();

        // Precondition: id is NOT in the registry
        kani::assume(!registry.contains_key(&id));

        let result = allowlist_check(&id, &registry);

        // MUST return Err(E-SRLZ-001) — never Ok
        kani::assert(
            matches!(result, Err(FerrochainError { code: "E-SRLZ-001", .. })),
            "unregistered id must return E-SRLZ-001"
        );
        kani::assert(
            result.is_err(),
            "Ok is unreachable for unregistered id"
        );
    }

    /// Positive: registered id returns Ok(())
    #[kani::proof]
    fn allowlist_passes_registered_id() {
        let mut registry: HashMap<Vec<String>, ()> = HashMap::new();
        let registered_id = vec!["langchain_core".to_string(), "prompts".to_string(), "PromptTemplate".to_string()];
        registry.insert(registered_id.clone(), ());

        let result = allowlist_check(&registered_id, &registry);
        kani::assert(result.is_ok(), "registered id must pass allowlist check");
    }

    /// Empty id always fails
    #[kani::proof]
    fn empty_id_is_always_rejected() {
        let registry: HashMap<Vec<String>, ()> = HashMap::new(); // even empty registry
        let result = allowlist_check(&[], &registry);
        kani::assert(
            matches!(result, Err(FerrochainError { code: "E-SRLZ-001", .. })),
            "empty id must always return E-SRLZ-001"
        );
    }
}
```

## Feasibility Assessment

**Feasibility: HIGH**

| Factor | Assessment | Notes |
|--------|-----------|-------|
| Input space size | Bounded | `id` path depth ≤ 4; each segment ≤ 16 printable ASCII bytes; 5 concrete registry entries — tractable symbolic HashMap lookup |
| Proof complexity | Low | The allowlist check is a single `HashMap::contains_key` call; Kani proves the conditional branch is always `Err` when the key is absent |
| Tool support | Supported | Kani 0.67.0; `allowlist_check` is pure-core sync; `HashMap<Vec<String>, ()>` lookup is modeled by Kani |
| Estimated proof time | < 5 min | Simple conditional reachability; HashMap lookup over bounded string keys converges quickly |

Key factors:
1. `Reviver::revive()` is pure-core sync — no I/O, no async (ADR-016 confirms; BC-2.19.005 confirms).
   Kani 0.67.0 compatible without any adaptation.
2. The critical proof is a reachability argument: prove that the `Ok` arm of `allowlist_check`
   is unreachable when `registry.contains_key(id) == false`. CBMC handles this as a trivial
   conditional reachability query.
3. The registry model (5 concrete entries + symbolic id ∉ registry) is representative of
   the production invariant: the security property holds for any registry size because it is
   a structural property of `contains_key`, not of the registry's specific contents.

**Registry modeling note:** The production `OnceLock<HashMap>` is initialized by `inventory`
linker constructors. Kani cannot introspect linker sections. The `allowlist_check` extraction
pattern — passing the registry as an explicit argument — makes the security property Kani-verifiable
without depending on linker initialization. The implementer must ensure `allowlist_check` is
callable with an externally-supplied registry reference so the harness can control its contents.

**Known constraint:** Kani's symbolic `String` / `Vec<String>` handling requires `kani::vec`
or manually bounded constructions. The harness above uses manual byte-level construction
with ASCII constraints to keep CBMC tractable. If CBMC loop-unwinding fails, reduce max
segment count from 4 to 2 or reduce segment byte length from 16 to 8.
