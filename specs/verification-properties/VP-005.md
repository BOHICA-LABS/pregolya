# VP-005: MultiServerMcpClient Holds No Live Connections

## Property Statement

A `MultiServerMcpClient` instance, after construction and before any tool invocation,
holds zero live connections to MCP servers. Connections are established lazily at
invocation time and not pooled or persisted across calls.

**Invariant (DI-014):** After `MultiServerMcpClient::new(configs)` returns, no network
connections are held. The client is a configuration object, not a live connection pool.

## Verification Strategy

**Tool:** Integration test (behavioral — not Kani-tractable; involves network state)

Red Gate test: `tests/red_gate/test_BC_2_09_005_mcp_no_live_connections.rs`

Test scenario: construct `MultiServerMcpClient` with valid configs pointing to mock
servers; assert that no TCP connections exist immediately after construction (verified
via port inspection or connection count); invoke a tool and assert a connection is
established; after invocation, assert connection is closed (if not pooled).

## Feasibility Assessment

**Feasibility: HIGH.** This is a behavioral test verifying connection lifecycle semantics.
The property is verified by inspecting connection state (OS-level or via mock transport)
before and after client construction and invocation.

**R11 context:** The upstream MCP adapter's `__aenter__` `NotImplementedError` contract
(Python async context manager) is the counter-example. Rust's lazy-connection model avoids
this class of issue by making connection establishment explicit at the call site.
