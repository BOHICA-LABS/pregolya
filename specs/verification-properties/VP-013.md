# VP-013: BashTool Risk Floor — ReadOnly and Low ActionRisk Always Return Err(E-TOOLS-007); Medium Is the Hard Floor

## Property Statement

For all `ActionRisk` variants `r` where `r` is `ReadOnly` or `Low`,
`check_risk_floor(r)` returns `Err(FerrochainError { code: "E-TOOLS-007", .. })`.
For all variants where `r` is `Medium` or `High`, `check_risk_floor(r)`
returns `Ok(())`. No code path permits `BashTool` to operate with `ActionRisk < Medium`.
The risk floor is an unconditional pure enum comparison — no runtime flag, no configuration
escape hatch.

**Formal invariant (DI-014):**
```
∀ r: ActionRisk:
  (r == ReadOnly ∨ r == Low) →
    check_risk_floor(r) == Err(FerrochainError { code: "E-TOOLS-007", category: VAL })
    ∧ check_risk_floor(r) ≠ Ok(())

∀ r: ActionRisk:
  (r == Medium ∨ r == High) →
    check_risk_floor(r) == Ok(())
    ∧ check_risk_floor(r) ≠ Err(_)
```

The comparison `risk < ActionRisk::Medium` is the complete floor check. `ActionRisk` is a
bounded enum (finite variants); Kani exhaustively enumerates all variants. The `Ok(())`
arm is structurally unreachable when `r ∈ { ReadOnly, Low }`.

## Source Contract

- **BC:** BC-2.23.005 — BashTool — Sandboxed Shell Execution; Non-Lowerable Medium Risk Floor; BashOutput; 256 KiB Output Cap; 30 s Timeout; E-TOOLS-004/007 (VP-013 Kani Seed)
- **ADR anchor:** ADR-020 Decision 3 — Risk Tier Defaults and HITL Integration; defines the `BashTool` `Medium` risk floor as a framework safety invariant non-lowerable by application configuration (`BashTool` risk tier CANNOT be lowered below `Medium`; attempting to set `ReadOnly` or `Low` returns a configuration error at startup)
- **Postcondition 4 (Risk floor violation):** `ToolConfig::override_risk(ActionRisk::ReadOnly)` or `override_risk(ActionRisk::Low)` returns `Err(E-TOOLS-007 BashRiskTierViolation: BashTool risk tier cannot be lowered below Medium; attempted: '<tier>')`.
- **Invariant — Risk floor:** `ToolConfig::override_risk(ActionRisk::ReadOnly)` and `ToolConfig::override_risk(ActionRisk::Low)` on a `BashTool` instance ALWAYS return `Err(E-TOOLS-007)`. No code path allows these tiers on BashTool. Pure enum comparison (`risk < ActionRisk::Medium` → error) with no side effects.
- **Invariant — DI-014:** Configuration errors propagate as `Err`; risk floor violation is never silently accepted as if the floor were not present.
- **EC-004:** `override_risk(ReadOnly)` at registry time → `Err(E-TOOLS-007)` — graph does not start.
- **EC-005:** `override_risk(Medium)` at registry time → accepted (Medium is the floor).
- **TV-005 (Red Gate):** `override_risk(ActionRisk::Low)` → `Err(E-TOOLS-007)` — `BashRiskTierViolation: BashTool risk tier cannot be lowered below Medium; attempted: 'Low'`.
- **TV-006:** `override_risk(ActionRisk::Medium)` → accepted; graph starts normally.

## Proof Method

| Method | Tool | Bounded? | Coverage |
|--------|------|----------|----------|
| Model checking | Kani 0.67.0 | Yes — `ActionRisk` is a finite enum (bounded variants: ReadOnly, Low, Medium, High — 4 variants; `#[non_exhaustive]`); Kani exhaustively enumerates all variants via `kani::any::<ActionRisk>()` if `kani::Arbitrary` is derived, or via explicit case enumeration | All ActionRisk variants; proves ReadOnly and Low → Err(E-TOOLS-007); Medium/High → Ok(()) |

**Kani async constraint (Kani 0.67.0 has NO native async support):**
`check_risk_floor(risk: ActionRisk) -> Result<(), FerrochainError>` is a pure-core
synchronous function in `ferrochain-tools::tools::shell`. No `.await`, no Tokio runtime,
no I/O — it is a pure enum comparison followed by an `Err` or `Ok` constructor. The Kani
harness calls it directly.

**Enum exhaustiveness:** `ActionRisk` is marked `#[non_exhaustive]` per CLAUDE.md conventions.
The Kani harness covers all four canonical variants (`ReadOnly`, `Low`, `Medium`, `High`)
via explicit case enumeration. If `ActionRisk` gains new variants in future cycles, the
harness must be updated and the floor rule re-evaluated for each new variant. The
risk-floor invariant assumes that any variant with lower authorization than `Medium` should
trigger `E-TOOLS-007`; the harness verifies the current variant set exhaustively.

**Harness boundary:** The proof covers `check_risk_floor` as a standalone pure function
extracted from `BashTool`'s registration logic. The full `ToolRegistry::register` flow
(which performs I/O and calls `check_risk_floor` as a validation step) is excluded from
the Kani scope. The proof establishes that the floor check is correct for all variants; the
registry integration is covered by behavioral tests.

## Proof Harness Skeleton

Target file: `ferrochain-tools/src/shell.rs`

```rust
// ferrochain-tools/src/proofs/risk_floor.rs
// Target fn: tools::shell::check_risk_floor

#[cfg(kani)]
mod proofs {
    use super::*;

    /// VP-013: Risk Floor — ReadOnly and Low always return Err(E-TOOLS-007).
    /// Proves: check_risk_floor(ReadOnly) == Err and check_risk_floor(Low) == Err.
    ///         check_risk_floor(Medium/High) == Ok.
    #[kani::proof]
    fn risk_floor_rejects_below_medium() {
        // Explicitly enumerate below-floor variants (ActionRisk is #[non_exhaustive])
        // — cannot use kani::any() if Arbitrary is not derived; explicit enumeration is safe

        // ReadOnly must be rejected
        let result_ro = check_risk_floor(ActionRisk::ReadOnly);
        kani::assert(
            matches!(result_ro, Err(FerrochainError { code: "E-TOOLS-007", .. })),
            "ReadOnly MUST return Err(E-TOOLS-007)"
        );
        kani::assert(result_ro.is_err(), "Ok is unreachable for ReadOnly");

        // Low must be rejected
        let result_low = check_risk_floor(ActionRisk::Low);
        kani::assert(
            matches!(result_low, Err(FerrochainError { code: "E-TOOLS-007", .. })),
            "Low MUST return Err(E-TOOLS-007)"
        );
        kani::assert(result_low.is_err(), "Ok is unreachable for Low");
    }

    /// VP-013 (positive): Medium and High pass the floor check.
    #[kani::proof]
    fn risk_floor_accepts_at_or_above_medium() {
        // Medium: the floor itself — must pass
        let result_med = check_risk_floor(ActionRisk::Medium);
        kani::assert(result_med.is_ok(), "Medium MUST pass the risk floor check");

        // High: the BashTool default — must pass
        let result_high = check_risk_floor(ActionRisk::High);
        kani::assert(result_high.is_ok(), "High MUST pass the risk floor check");
    }

    /// VP-013 (exhaustive): enumerate all known variants via symbolic choice.
    /// This harness verifies the COMPLETE floor rule for all variants simultaneously.
    /// Requires kani::Arbitrary derived for ActionRisk, or a symbolic bool approach.
    #[kani::proof]
    fn risk_floor_exhaustive_coverage() {
        // Encode ActionRisk as a bounded integer (0=ReadOnly, 1=Low, 2=Medium, 3=High)
        // 4 canonical variants per interface-definitions.md §PreToolCallHook
        let idx: u8 = kani::any();
        kani::assume(idx <= 3);

        let risk = match idx {
            0 => ActionRisk::ReadOnly,
            1 => ActionRisk::Low,
            2 => ActionRisk::Medium,
            _ => ActionRisk::High,
        };

        let result = check_risk_floor(risk);

        // Floor invariant: idx < 2 (ReadOnly or Low) → Err; idx >= 2 → Ok
        if idx < 2 {
            kani::assert(
                matches!(result, Err(FerrochainError { code: "E-TOOLS-007", .. })),
                "risk below Medium MUST return E-TOOLS-007"
            );
        } else {
            kani::assert(result.is_ok(), "risk at or above Medium MUST return Ok");
        }
    }
}
```

## Feasibility Assessment

**Feasibility: HIGH**

| Factor | Assessment | Notes |
|--------|-----------|-------|
| Input space size | Trivially bounded | `ActionRisk` is a 4-variant enum; explicit enumeration covers all variants in a single harness iteration |
| Proof complexity | Very Low | The function is a single comparison `risk < ActionRisk::Medium` followed by an `Err` or `Ok` constructor. No arithmetic, no loops, no I/O |
| Tool support | Supported | Kani 0.67.0; `check_risk_floor` is pure-core sync; enum comparison is trivially modeled by CBMC |
| Estimated proof time | < 1 min | 4-variant enum exhaustion; CBMC solves in seconds |

Key factors:
1. `check_risk_floor` is a pure-core synchronous function — no I/O, no async, no state.
   Kani 0.67.0 compatible without any adaptation.
2. The proof is an exhaustive enumeration over 4 variants. CBMC's SAT solver handles this as 4
   independent evaluations of a single boolean expression.
3. The risk-floor invariant is structurally imposed by the ordering of `ActionRisk` variants.
   If `ActionRisk` uses `#[repr(u8)]` with ordering `ReadOnly=0, Low=1, Medium=2, High=3`,
   the floor check `risk < ActionRisk::Medium` (i.e., `risk < 2`) is equivalent to a simple
   integer comparison — trivially CBMC-tractable.

**Known constraint:** `ActionRisk` is `#[non_exhaustive]`. Future variants added between
`Low` and `Medium` in the ordering would break the floor invariant unless explicitly handled
in `check_risk_floor`. The implementer must ensure the comparison uses the variant ordering,
not ordinal position, or uses an explicit allowlist of above-floor variants. The harness
must be updated whenever `ActionRisk` gains new variants.

**Note on `category` field:** error-taxonomy.md §Component: TOOLS (registered at D23) registers `E-TOOLS-007` with
`category: VAL` (configuration validation error — same reasoning as E-RETRY-004, E-SBXD-006,
E-SPLIT-001/002). The Kani harness assertion uses `code: "E-TOOLS-007"` for the primary
check; the `category` field in the `FerrochainError` struct MUST be `Category::Val` per the
error-taxonomy. BC-2.23.005 was amended to `VAL` in burst-232 (v1.1) — consistent with this VP.
