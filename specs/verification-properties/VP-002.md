# VP-002: Session Triple-Address Uniqueness

## Property Statement

Every state operation is addressed by the triple (thread_id, checkpoint_ns, checkpoint_id).
No two distinct triples map to the same storage address. The triple flows from the trait
method signature to the SQL WHERE clause without collapsing.

**Formal invariant (DI-005):** `∀ s1 ≠ s2: SessionKey, storage_address(s1) ≠ storage_address(s2)`

## Kani Harness Skeleton

Target file: `ferrochain-checkpoint/src/session_index.rs`

```rust
#[cfg(kani)]
mod proofs {
    use super::*;

    /// VP-002: Session Triple-Address Uniqueness
    /// Proves: no two distinct SessionKeys produce the same storage address.
    #[kani::proof]
    fn session_triple_uniqueness() {
        let s1: SessionKey = kani::any();
        let s2: SessionKey = kani::any();

        // If the keys differ, their addresses must differ
        kani::assume(s1 != s2);

        let addr1 = storage_address(&s1);
        let addr2 = storage_address(&s2);

        kani::assert(addr1 != addr2, "Distinct session keys must map to distinct addresses");
    }

    /// Negative invariant: bare thread_id alone does not address state
    #[kani::proof]
    fn no_bare_thread_id_addressing() {
        let thread_id: ThreadId = kani::any();
        let ns1: CheckpointNamespace = kani::any();
        let ns2: CheckpointNamespace = kani::any();
        let id1: CheckpointId = kani::any();
        let id2: CheckpointId = kani::any();

        // Two different full triples sharing the same thread_id
        let s1 = SessionKey { thread_id: thread_id.clone(), checkpoint_ns: ns1, checkpoint_id: id1 };
        let s2 = SessionKey { thread_id: thread_id.clone(), checkpoint_ns: ns2, checkpoint_id: id2 };

        kani::assume(s1 != s2); // different full triples

        // Their addresses must still differ (ns or id differs)
        let addr1 = storage_address(&s1);
        let addr2 = storage_address(&s2);

        kani::assert(addr1 != addr2, "Same thread_id but different ns/id must have different addresses");
    }
}
```

## Feasibility Assessment

**Feasibility: HIGH**

Key factors:
1. `storage_address` is a pure function: `SessionKey → StorageAddress` (e.g., a composite SQL primary key tuple).
2. `SessionKey` is a plain struct over bounded symbolic values; `kani::Arbitrary` derivable.
3. The proof is simple injection check: if inputs differ, outputs differ. No unbounded loops.
4. `CheckpointId` is `u64` (ADR-005), `ThreadId` is a bounded string, `CheckpointNamespace` is a bounded string.

**Known constraint:** `ThreadId` and `CheckpointNamespace` are `String` types. Kani requires
bounded strings. The harness must constrain string lengths: `kani::assume(thread_id.len() <= 64)`.

**Key insight:** `storage_address` maps the triple to a SQL composite key. The proof guarantees
that the mapping is injective — a property of the address function itself, not the database.
The database PRIMARY KEY constraint enforces uniqueness at runtime; Kani proves the address
function is injective by construction.

## Proof Obligations

- [ ] `SessionKey` implements `kani::Arbitrary` with bounded string fields
